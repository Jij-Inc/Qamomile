# Qamomile v0.16.0

Qamomile v0.16.0 uses a Rust compiler to verify quantum programs written in Python. If you are upgrading from v0.15.2, the main changes are how you run a kernel, read its measurements, and estimate the qubits and gates it needs. If you are already using RC1, see [Changes since RC1](#v0160-rc1-changes).

```bash
pip install qamomile==0.16.0
```

## Program checks in the Rust compiler

In v0.15.x, you imported `qamomile.circuit as qmc` and decorated a Python function with `@qmc.qkernel` to define a quantum kernel. Qamomile ran the function with placeholder inputs and recorded its operations. In v0.16.0, use `import qamomile as qm` and `@qm.qkernel`. Qamomile reads the function's source code. The Rust compiler checks the types and tracks where each quantum state is used. Both compilation and resource estimation work from this checked program.

Qamomile also includes a new built-in simulator written in Rust, `qm.Reference()`. With the base Qamomile installation, you can run the verified quantum program on your computer and inspect its measurement results.

## Compiling and running a quantum kernel

In v0.15.x, you combined a target-specific transpiler, such as `QiskitTranspiler`, with an executor. In v0.16.0, use `qm.specialize()` to fix constants, `qm.compile(..., to=...)` to convert the program for a target, and `qm.run(..., on=...)` to run it on an execution endpoint.

Annotate each kernel argument according to when you supply its value. Use `Const` for a value you fix before compilation and `Param` for a value you supply at each run. The example below uses the same `reference` object for compilation and execution.

```python
import qamomile as qm

@qm.qkernel
def biased_coin(n: qm.Const[qm.Int], theta: qm.Param[qm.Real]) -> qm.Shot[qm.Bits[1]]:
    state = qm.qubits(1)
    for _ in range(n):
        state = qm.ry(state, theta)
    return qm.measure(state)

reference = qm.Reference()
program = qm.specialize(biased_coin, n=3)
artifact = qm.compile(program, to=reference)
record = qm.run(
    artifact, on=reference, parameters={"theta": 0.0}, shots=8, seed=7
)
assert record.result.counts == {(0,): 8}
```

Here, `qm.specialize(biased_coin, n=3)` fixes the number of rotations at three. You pass the rotation angle `theta` to `qm.run()` in `parameters`. At angle zero, all eight measurements give `(0,)`. To try a different angle, run the same `artifact` with `parameters={"theta": 0.5}`. A `Shot` value, such as the measured bit, is determined during each trial. For a walkthrough, see [Your First Quantum Kernel](../tutorial/01_your_first_quantum_kernel.ipynb).

## Measurement results and expectation values

In v0.15.x, you used `executable.sample()` for repeated measurements and `executable.run()` for a single execution or an expectation value computed with `expval` inside the kernel. In v0.16.0, `qm.run()` returns a `RunRecord` with the execution settings and results. When sampling a bit register, `record.result.counts` gives the number of occurrences of each outcome.

To estimate an observable, pass the kernel that prepares the state and the observable to `qm.expectation()`. It returns the estimate and its standard error. For example, the zero state gives +1 on every measurement of Z.

```python
@qm.qkernel
def prepare_zero() -> qm.Q[qm.Bits[1]]:
    return qm.qubits(1)

estimate = qm.expectation(
    prepare_zero, qm.Z(0), on=reference, shots=8, seed=7
)
assert estimate.value == 1.0
assert estimate.standard_error == 0.0
```

## From affine to linear quantum types and automatic uncomputation

In v0.15.x, a `Qubit` or `Vector[Qubit]` could be left unused. In v0.16.0, `Q[T]` represents a quantum state. After a gate, you pass the updated state to the next operation. The compiler checks that each version is consumed exactly once, for example by another gate, a measurement, a return, or an explicit `qm.discard()`.

The compiler can also undo a computation on temporary qubits and release them automatically (automatic uncomputation). In the following example it applies the inverse of T followed by H to `scratch`, then releases the qubit.

```python
@qm.qkernel
def with_scratch() -> qm.Shot[qm.Bits[1]]:
    scratch = qm.qubits(1)
    scratch = qm.h(scratch)
    scratch = qm.t(scratch)
    return qm.measure(qm.prepare((1,)))
```

If the compiler cannot establish that a temporary state can be safely uncomputed, you must account for it explicitly. For example, you can return or measure it, or use `qm.discard()` to drop it. Discarding a state does not undo its gates.

## Changes to the resource estimation interface

In v0.15.x, you called `kernel.estimate_resources()` on a quantum kernel to get its resource estimate. In v0.16.0, you pass the quantum program to `qm.resources.logical(program)` and select the metrics you need from the returned `ResourceStudy`. The example below retrieves the logical gate count and the maximum number of qubits in use at the same time.

```python
study = qm.resources.logical(program)
gates = study.metric(qm.resources.LOGICAL_GATES)
qubits = study.metric(qm.resources.LOGICAL_PEAK_QUBITS)
```

A metric can include bounds, assumptions, and reasons that an exact count is unknown. See [Resource Estimation](../tutorial/04_resource_estimation.ipynb) for examples of reading these estimates.

## Standard library for quantum operations

In v0.15.x, reusable algorithms and standard functions lived in `qamomile.circuit.algorithm` and `qamomile.circuit.stdlib`. Import them from `qamomile.stdlib` in v0.16.0. Some operations keep their names but take and return the new quantum types. For example, the quantum Fourier transform (`qft`) takes the register and its width and returns the transformed register.

```python
from qamomile.stdlib import qft

@qm.qkernel
def fourier_sample() -> qm.Shot[qm.Bits[2]]:
    state = qm.qubits(2)
    state = qft(state, 2)
    return qm.measure(state)
```

For a two-dimensional example, the [multidimensional QFT tutorial](../algorithm/multidimensional_qft.ipynb) splits a register into x and y coordinates and applies `qft` to each.

## QSVT phases from a polynomial

In v0.15.x, you supplied the phases for `qsvt()` (quantum singular value transformation). In v0.16.0, `synthesize_qsvt_polynomial()` takes Chebyshev coefficients, generates the phases, and checks how closely the real part of the response matches the target polynomial over $[-1, 1]$. You can pass its result directly to `qsvt()`. The example requests the polynomial $p(x)=x/2$ with an error of at most $10^{-6}$.

```python
from qamomile.stdlib import synthesize_qsvt_polynomial

polynomial = synthesize_qsvt_polynomial([0.0, 0.5], max_error=1e-6)
assert polynomial.uniform_error_bound <= 1e-6
```

The synthesis supports polynomials subject to parity and coefficient constraints. For a block encoding (a matrix embedded in part of a quantum operation after normalization) with zero reconstruction error, `reciprocal_svt()` also constructs an approximation to the reciprocal function given a positive lower bound on the smallest singular value.

## Block encoding for SciPy sparse arrays

You can now pass a SciPy sparse array such as `csr_array` to `sparse_access_block_encoding()`. It accepts square matrices of power-of-two dimension starting at two, including complex and nonsymmetric matrices. The returned encoding reports the normalization factor (`normalization`) and an upper bound on the matrix reconstruction error (`error_bound`).

This example requires `qamomile[sparse]` for SciPy sparse arrays.

```python
from scipy.sparse import csr_array
from qamomile.stdlib import sparse_access_block_encoding

matrix = csr_array([[1.0, 0.0], [0.0, 0.5]])
encoding = sparse_access_block_encoding(matrix, max_error=1e-8)
assert encoding.error_bound <= 1e-8
```

## Migrating to QAOAExperiment

:::{note}
We are still refining the optimization interface described here. We plan to change how you use classes such as `QAOAExperiment` in the near future.
:::

If you used `QAOAConverter` in v0.15.x, use `QAOAExperiment` to group the optimization problem and circuit settings. For the quantum approximate optimization algorithm (QAOA), you can fix the problem and number of layers, compile once, and try different angles. This example runs one set of angles. For an example that searches for good angles, see [QAOA for Max-Cut](../algorithm/qaoa_maxcut.ipynb).

```python
from qamomile.optimization import BinaryModel, QAOAExperiment

model = BinaryModel.from_hubo({(0,): -1.0, (1,): -1.0, (0, 1): 2.0})
experiment = QAOAExperiment(model, layers=1)
compiled = experiment.compile(to=reference)
result = compiled.run(
    on=reference, gammas=[0.0], betas=[0.0], shots=8, seed=7
)
```

The [OMMX benchmark tutorial](../integration/ommx_quantum_benchmarks_qaoa.ipynb) compares QAOA with the classical solver SCIP on the same binary optimization problem.

## Customizing compiler optimizations

In v0.16.0, you can choose which optimizations the compiler applies and in what order. Define the sequence with `OptimizationPipeline` and pass it to `qm.compile()` using the `optimizer` argument.

```python
from qamomile.compilation import OptimizationPipeline

optimizer = OptimizationPipeline.multilevel(family=False)
optimized = qm.compile(program, to=reference, optimizer=optimizer)
```

Use `append()` to add a transformation or `replace()` to substitute one. Rust checks the types and structure of the transformed program. If you write a custom transformation, you are responsible for preserving the computation's result.

## Cirq execution and QIR export

You can now compile and run a kernel with Cirq. The following example runs the `program` defined above on the Cirq simulator by changing the endpoint passed to `qm.run()`.

This example requires `qamomile[cirq]` for the Cirq simulator.

```python
from qamomile.cirq import CirqSimulator

cirq_record = qm.run(
    program, on=CirqSimulator(),
    parameters={"theta": 0.0}, shots=8, seed=7,
)
```

To export a circuit for an external tool, compile directly to QIR (Quantum Intermediate Representation) and read its text with `load_ir()`.

This example requires `qamomile[qir]` to export QIR.

```python
from qamomile.qir import QIR, load_ir

qir_artifact = qm.compile(fourier_sample, to=QIR())
qir_text = load_ir(qir_artifact)
```

The QIR target supports QIR 1.0 Base Profile, which requires a circuit structure fixed in advance. Runtime parameters, branches on measurement results, and gates after a measurement are unsupported.

## Changes since RC1

If you are upgrading from [v0.16.0 RC1](v0_16_0_rc1), check these changes in existing code and saved programs.

- **Single-bit measurements.** `measure()` and `measure_reset()` on a `Q[Bool]` state now produce an integer `0` or `1` for the measured bit. The measured bit from `measure_x()`, `measure_y()`, and `measure_z()` follows the same rule. If your kernel returns that bit, change its return annotation from `qm.Shot[qm.Bool]` to `qm.Shot[qm.Bit]`. Rebuild saved programs that declared these measurements as Boolean from their source. Previously saved results retain their original Boolean values.
- **Random seeds.** The default changed from `seed=0` to `seed=None`, which leaves randomness to the execution endpoint. To reproduce the RC1 setting on a simulator such as `qm.Reference()`, pass `seed=0` explicitly. `QurationLocal` requires an integer seed, and endpoints without seed control require `None`.
- **Rotation and phase angles.** Qamomile checks that the final angle is finite before executing a circuit. Recompile saved circuit artifacts containing rotations from source so they include this check.
- **IBM Runtime dependency.** `qamomile[qiskit]` now requires `qiskit-ibm-runtime>=0.51,<1`. If you used `qamomile[qbraid]` to install IBM Runtime as well, include `qamomile[qiskit]` as well.
- **Current shot number.** Within a kernel, `qm.get_current_shot()` returns the shot number, starting at zero for each run. In this example, only the first of five shots returns `True`.

  ```python
  @qm.qkernel
  def first_shot() -> qm.Shot[qm.Bool]:
      return qm.get_current_shot() == 0

  result = qm.run(first_shot, on=qm.Reference(), shots=5).result
  assert result.values == {True: 1, False: 4}
  ```

- **IBM Runtime job validation.** With an eligible IBM Quantum account, set `IBMRuntime(backend=backend, dry_run=True)` to validate a sampling job in IBM's cloud without using quantum processor time. IBM supports this check in job and Batch modes.

  For a compiled circuit, `qm.execute()` returns the validation report (`ValidationResult`) directly. With `qm.run()`, read the report from `record.result`. With `qm.submit()`, call `job.result()` on the returned job. The report’s `metadata()["usage"]` includes the estimated processor time for a hardware run. Estimates that are still pending appear as `None`. The [Qiskit integration guide](../integration/qiskit_support.ipynb) shows how to use the same compiled circuit for validation and execution.

### Bug fixes

- **Register and array widths in helper kernels.** When you call the same kernel with different widths, both the compiled circuit and `qm.resources.logical()` now use the width from each call. For example, if a helper applies one rotation per element and you pass it rows of lengths two and three, both the circuit and the estimate give five rotations in total.
- **Reusing a Qiskit circuit with a vector of angles.** When a vector's length is fixed at compilation, you can use `row[len(row) - 1]` or `row[-1]` as a rotation angle, compile the circuit once, and pass a different vector on each run.
- **Uniformly controlled Y rotations.** With six control qubits, `uniformly_controlled_ry()` and `uniformly_controlled_ry_from_angles()` now compile and run a circuit that selects among 64 angles. RC1 could exceed the kernel call-depth limit for this circuit. The [option pricing tutorial](../algorithm/option_pricing.ipynb) shows how to apply a different rotation for each price.
- **Constant QSVT polynomials.** For a constant polynomial, RC1 shifted the single phase by an extra $-\pi/2$. This affected both `QSVTPhases.from_qsp_wx()` and circuits built with `synthesize_qsvt_polynomial()`, and could change the outcome of a controlled QSVT circuit. Regenerate affected circuits from the original phase or coefficients.
- **Two-variable QRAC groups.** When a (3,2) quantum random access code (`QRACVariant.QRAC32`) placed exactly two variables in a group, RC1 used too small a scale factor for those variables in the Hamiltonian (the operator that represents the model's energy). If your encoding contains such a group, regenerate the Hamiltonian from the original model.
- **Reusing Qiskit circuits.** In RC1, setting a rotation angle in a loop on a circuit returned by `load_circuit()` could also change the angle in a later run of the compiled program. Each run now uses its own parameter values.
- **QURI Parts measurement counts.** `QuriPartsSampler` now accepts NumPy integers for both the measured basis state and its count. In RC1, these valid results could raise an `ExecutionError`.
- **Measurement-dependent `if` statements.** The compiler now skips constants that neither branch uses when passing values into the branches. This fixes a compilation error that could occur when a large integer constant such as `2**31` was first used after the `if` statement.
