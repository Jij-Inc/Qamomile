# Qamomile v0.16.0 RC1

> **This is the first release candidate (RC1). The specifications and APIs described here may change before the final release.**

Qamomile v0.16.0 RC1 moves the compiler core to Rust and substantially revises how programs are defined, verified, and executed. You can still write quantum programs in Python, but this release makes broad changes to the interfaces used through v0.15.x. This note introduces the main changes.

The code below uses the new v0.16.0 RC1 syntax. Examples that use Qiskit Aer require the Qiskit integration. Later examples reuse `endpoint` and `program` from the first example.

## Verify program rules with Rust at the core

Through v0.15.x, Qamomile implemented its compiler processing in Python. It transformed the syntax of quantum kernels written in Python, then used tracing to create an intermediate representation by running the functions with placeholder inputs and recording their operations.

In v0.16.0 RC1, Qamomile builds programs from source code without executing the kernel's function body as Python. Python parses the source and creates typed HIR (an intermediate representation close to the source). Rust verifies types and how quantum values are used, then converts the program to QCore (Qamomile's common intermediate representation). Resource analysis and conversion for execution targets also use this verified representation.

You do not need to write Rust. You continue to write quantum programs in Python.

## Common operations for fixing constants, compiling, and running

In v0.15.x, you combined a Transpiler, such as `QiskitTranspiler`, with an Executor.

In v0.16.0 RC1, you use common operations: `specialize` to fix constants, `compile` to convert a program, and `run` to execute it. Specify the compilation target with `compile(..., to=...)` and the execution endpoint with `run(..., on=...)`. You can pass a kernel directly to `run` to handle conversion and execution together, or pass a compiled program.

```python
import qamomile as qm
from qamomile.qiskit import Aer

@qm.qkernel
def biased_coin(theta: qm.Param[qm.Real]) -> qm.Shot[qm.Bits[1]]:
    state = qm.qubits(1)
    state = qm.ry(state, theta)
    return qm.measure(state)

endpoint = Aer()
program = qm.specialize(biased_coin)
artifact = qm.compile(program, to=endpoint.target)
record = qm.run(
    artifact, on=endpoint, parameters={"theta": 0.0}, shots=8, seed=7
)
counts = record.result.counts
```

In addition to a value's type, you declare when the value becomes fixed. `Const[T]` values are fixed at `specialize` time, `Param[T]` values at `run` time (when execution starts), and `Shot[T]` values during a single shot. The rotation angle in this example is a `Param`, so you can reuse the compiled program and change the angle for each run.

## Changes to measurement and expectation value entry points

In v0.15.x, you used `executable.sample()` for repeated measurements and `executable.run()` for a single execution or an expectation value calculation with `expval` inside a kernel.

In v0.16.0 RC1, you execute kernels that contain measurements with `qm.run()` and receive a `RunRecord` (a record of the execution settings and results). In the example above, `record.result.counts` gives the count for each measured value.

Use `qm.expectation()` for the expectation value of an observable. Pass a kernel that prepares a quantum state and an observable, rather than measured values, to receive an estimate and its standard error. The return value of `run()` does not automatically switch to an expectation value.

```python
@qm.qkernel
def prepare_zero() -> qm.Q[qm.Bits[1]]:
    return qm.qubits(1)

estimate = qm.expectation(
    prepare_zero, qm.Z(0), on=endpoint, shots=8, seed=7
)
value = estimate.value
error = estimate.standard_error
```

## Linear quantum types and automatic uncomputation

In v0.15.x, quantum values were represented by `Qubit` or `Vector[Qubit]` and followed affine rules (each state could be used at most once, and could be left unused). In v0.16.0 RC1, quantum states are represented by `Q[T]`. Rust verifies linear rules that require each state at each point to be passed on exactly once, for example by returning or measuring it. As part of this change, we introduced `discard`, a function that explicitly discards an unwanted quantum state. However, `discard` only explicitly discards the state. It does not undo the preceding computation to restore the initial state.

We also introduced auto uncomputation (automatic insertion of inverse operations that undo an unneeded computation and restore the initial state). For scratch quantum states that the compiler can confirm are safe to uncompute, it automatically inserts inverse operations and deallocation. When the compiler can confirm that auto uncomputation is possible, you can leave quantum values unused as under affine rules, without explicitly calling `discard`.

```python
@qm.qkernel
def with_scratch() -> qm.Shot[qm.Bits[1]]:
    scratch = qm.qubits(1)
    scratch = qm.h(scratch)
    scratch = qm.t(scratch)
    return qm.measure(qm.prepare((1,)))
```

In this example, the compiler automatically inserts inverse operations and deallocation for `scratch`. This does not apply to every unused state. For quantum inputs received from outside, or scratch space connected to a state retained as output, you need to write an operation such as a return, measurement, or explicit discard.

## Obtain resource estimates as a ResourceStudy

The `kernel.estimate_resources()` API from v0.15.x changes to `qm.resources.logical(...)` in v0.16.0 RC1. The new return value is a `ResourceStudy`. Use `metric()` to select metrics such as qubit count or gate count.

```python
study = qm.resources.logical(program)
gates = study.metric(qm.resources.LOGICAL_GATES)
qubits = study.metric(qm.resources.LOGICAL_PEAK_QUBITS)
```

The new estimates handle lower and upper bounds, assumptions, and unknown factors as well as values.

## Consolidate quantum components from algorithm and stdlib into stdlib

Reusable quantum algorithm components and standard functions, previously split between `qamomile.circuit.algorithm` and `qamomile.circuit.stdlib` in v0.15.x, are now together in `qamomile.stdlib`. Import components such as QFT from this package to use them in kernels.

```python
from qamomile.stdlib import qft

@qm.qkernel
def fourier_sample() -> qm.Shot[qm.Bits[2]]:
    state = qm.qubits(2)
    state = qft(state, 2)
    return qm.measure(state)
```

Even when an algorithm keeps the same name, its arguments and return values have changed to match the new quantum types.

## Signal and Response for composing quantum operations

This release adds `Signal` and `Response` for combining quantum operations. These were not available in v0.15.x. Use `Region` to select input and output bit conditions, and treat the transformation between them as a `Signal`. You can form products and weighted sums, and generate quantum operations that transform singular values (values that describe how much a matrix stretches or compresses) using a polynomial specified by a `Response`.

The following example selects the part where the first bit is 0 and creates a transformation that halves the singular values.

```python
import qamomile as qm
from qamomile.stdlib import Region, Response, response, select

@qm.qkernel
def transform(state: qm.Q[qm.Bits[2]]) -> qm.Q[qm.Bits[2]]:
    return qm.h(state, target=0)

signal = select(transform, input=Region("0*"), output=Region("0*"))
transformed = response(signal, Response.chebyshev([0.0, 0.5]))
```

## QSVT phase synthesis and approximation error verification

QSVT (quantum singular value transformation) was already available in v0.15.x, but you had to supply the phase sequence for the general-purpose `qsvt()` function. In v0.16.0 RC1, we added `synthesize_qsvt_polynomial()` to generate a phase sequence from the coefficients of a Chebyshev polynomial (a type of polynomial often used to approximate functions). It verifies the approximation error between the real part of the synthesized response and the target polynomial over `[-1, 1]`. You can pass the returned object directly to `qsvt()`.

```python
from qamomile.stdlib import synthesize_qsvt_polynomial

# Approximate p(x) = 0.5 * x.
polynomial = synthesize_qsvt_polynomial([0.0, 0.5], max_error=1e-6)
assert polynomial.uniform_error_bound <= 1e-6
```

There are constraints on the parity and coefficient magnitudes of supported polynomials. We also added `reciprocal_svt()`, which constructs a transformation that approximates the reciprocal function for a block encoding (a representation that normalizes a matrix and embeds it in part of a quantum operation) with zero reconstruction error, given a lower bound on the smallest singular value.

## Construct block encodings from SciPy sparse arrays

In v0.16.0 RC1, we added `sparse_access_block_encoding()` to construct block encodings from SciPy sparse arrays (arrays that primarily store nonzero elements). This matrix input method was not available in v0.15.x. You can pass arrays such as `csr_array` directly. Complex and nonsymmetric matrices are also supported.

```python
from scipy.sparse import csr_array
from qamomile.stdlib import sparse_access_block_encoding

matrix = csr_array([[1.0, 0.0], [0.0, 0.5]])
encoding = sparse_access_block_encoding(matrix, max_error=1e-8)
```

The normalization factor is available as `normalization`, and the upper bound on matrix reconstruction error as `error_bound`.

## Move mathematical optimization from Converter to Experiment

In v0.15.x, classes such as `QAOAConverter` were central to converting problems into quantum circuits. In v0.16.0 RC1, you use an Experiment, such as `QAOAExperiment` (an experiment that bundles a problem and its settings).

You can compile with a fixed problem and layer count, then run with different runtime parameters, such as angles. The following example shows how to run QAOA. It does not include an optimization loop to find the angles.

```python
from qamomile.optimization import BinaryModel, QAOAExperiment

model = BinaryModel.from_hubo({(0,): -1.0, (1,): -1.0, (0, 1): 2.0})
experiment = QAOAExperiment(model, layers=1)
compiled = experiment.compile(to=endpoint.target)
result = compiled.run(
    on=endpoint, gammas=[0.0], betas=[0.0], shots=8, seed=7
)
```

## A way to add quantum kernel optimizations

Although v0.15.x already had operations such as constant evaluation and circuit replacement, v0.16.0 RC1 lets you select and extend optimizations by passing an `OptimizationPipeline` (which specifies a combination of transformations and their order) to `optimizer=`.

```python
from qamomile.compilation import OptimizationPipeline

optimizer = OptimizationPipeline.multilevel(family=False)
optimized = qm.compile(program, to=endpoint.target, optimizer=optimizer)
```

Use methods such as `append()` and `replace()` to add or replace custom transformations. The transformed program also passes through Rust verification. However, type and structure verification does not automatically prove that a custom transformation preserves the same computation results.

## Cirq integration and direct QIR output

In addition to integrations such as Qiskit that were available in v0.15.x, we added conversion and execution for Cirq. The `qm.run(..., on=...)` call stays the same when you change the execution endpoint. The next example requires the Cirq integration.

```python
from qamomile.cirq import CirqSimulator

cirq_record = qm.run(
    biased_coin, on=CirqSimulator(),
    parameters={"theta": 0.0}, shots=8, seed=7,
)
```

You can also output QIR directly. This is a separate entry point from the previous QIR support through HUGR. The next example requires the QIR integration.

```python
from qamomile.qir import QIR, load_ir

qir_artifact = qm.compile(fourier_sample, to=QIR())
qir_text = load_ir(qir_artifact)
```

QIR is an output format for external systems, rather than an execution endpoint within Qamomile. It currently targets QIR 1.0 Base Profile, where the circuit structure is fixed in advance. Runtime parameters, branches based on measurement results, and gates after measurement are not supported.

The H2 integration added in v0.15.2 is not supported in v0.16.0 RC1.
